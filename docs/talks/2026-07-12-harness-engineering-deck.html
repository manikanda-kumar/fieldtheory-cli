Harness Engineering

From chat loops to "harness is all you need"—and how to build for the model path.

Agent = Model + Harness. Evolve the loop, don't cage the intelligence.

Act I · Migration of the Interface

The core question of modern agentics

Why do two teams using the exact same LLM API get entirely different product reliability and outputs?

The Raw Approach

Direct API prompts, implicit trust, vibe-based iterations without validation layers.

The Engineered Approach

Structured tool schemas, sandbox execution, AST policies, and regression evals.

Citations: Viv Trivedy · D7 · 2026 | Jerry Liu · F1 · 2025

Speaker notes

The difference lies entirely in the engineering of the harness. A raw model behaves probabilistically and breaks under edge cases. An engineered harness wraps the model in structured execution, verification, and recovery loops. Skip details on compiler errors if short on time.

Chat was the interface

Early LLM user experience was conversation. We locked capabilities inside a single prompt-and-response text window.

  • Manual copy-pasting of editor code
  • State was held in user's attention, not the machine
  • No programmatic validations or isolated feedback loops

Speaker notes

In 2023, LLM interaction meant chatting. The user carried the state in their head and manually copied output to their editor. Schmid points out that chat was an interface bottleneck, masking the actual programmatic potential of models. Move quickly to copilot.

Copilots shifted the context loader closer to the code. However, they were still constrained to single-turn autocomplete. The engineer still acted as the compiler and verification harness, manually testing and debugging every generated suggestion.

Act I · Migration of the Interface

"Bash is all you need"

Giving models access to a raw shell and terminal loop felt like the ultimate tool unlock. Minimal constraints, maximum action.

  • Model outputs command as a string
  • Harness executes command directly in directory
  • Stdout/stderr fed straight back into context
Citations: [speaker claim] | HumanLayer Blog · E1 · 2026

Speaker notes

We realized that giving models tool access meant giving them terminal access. The "bash is all you need" phase prioritized raw power. But without structured isolation, a single bad command could delete a database or trigger an infinite loop of pip installs.

Act I · Migration of the Interface

Then agents hit the wall

Unconstrained loops run out of gas. Raw tool execution crashes into system complexity and safety limits.

  • Context Dilution: Infinite logs forget base goals
  • Tool Thrashing: Loops repeat failing actions
  • Silent Breakages: Tests pass but modules break
Citations: Anthropic Engineering · B1 | Pamela Fox · F9 | Kenton Varda · F10

Speaker notes

Autonomy without guardrails degrades quickly. Anthropic found that long-running agents thrash when tool outputs are too verbose. Fox highlighted how specs drift silently, and Varda showed that agents require fine-grained capability-based permissions, not root shell access.

Act II · What a Harness Is

Vocabulary: Framework, Runtime, Harness

To engineer systems, we must disambiguate the stack. They are not interchangeable terms.

  • Framework: Abstract chain elements & prompts
  • Runtime: Graph executing nodes & persistence
  • Harness: The opinionated outer loop productized
Citations: LangChain Blog · A2 · 2025

Speaker notes

A framework like LangChain or Pydantic AI is how you assemble nodes. The runtime is the execution engine. But the harness is the product itself—the specific sequence of context loaders, sandbox isolation, lint rules, and test loops that make the agent reliable. Skip definition details if short.

Act II · What a Harness Is

Memory: progress logs over vector search

For long-horizon tasks, keeping states in structured files beats hoping the context window remembers.

  • Checkpoint file system states explicitly
  • Commit steps iteratively in git
  • Read checkpoint state logs at start of next turn
Citations: Anthropic Engineering · B1 | dabit3 · E4

Speaker notes

Rather than dumping raw chats or relying on embeddings, high-performing harnesses force agents to write their own checkpoint files on disk. The next turn reads the file first. Low-tech, deterministic memory scales better than high-tech context stuffing.

Act II · What a Harness Is

Opinionated agents win

Giving an agent too many choices leads to path paralysis. Encode engineering taste directly into the harness defaults.

  • Constrain tools to direct interfaces
  • Format styles, checkout configurations and paths are preset
  • Limits backtracking loops
Citations: Viv Trivedy · D2 · 2026

Speaker notes

Trivedy argues that agents fail when they have too many tools. The best harnesses limit options and enforce a clear protocol. By narrowing the action space, you reduce model error and keep the execution focused and predictable.

Act III · Engineering the Harness

Context is load-bearing

Tension: When should we load skills into the model's active context versus when should we delegate to subagents?

Skills (In-Context)

Injected prompt sheets. Fast, but risks attention degradation under load.

Subagents (Delegated)

Isolated child loop workspace. Clean, but high communication latency.

Citations: dexhorthy · E2 · 2026 | LangChain Memory · C4 · 2026

Speaker notes

This is tension slide 1 (debate slide). Packing too many instructions degrades attention. A good harness balances this: keep the main agent thin, inject highly specific skills just-in-time, and spawn isolated subagents for heavy sub-tasks. Skip subagent setup details if short on time.

Act III · Engineering the Harness

Tools are contracts

Vague tool schemas cause failures that look like "dumb models." Define strict, deterministic boundaries for every tool.

Vague edit_file()

Model guesses lines, replaces entire buffer, breaks local indentation structure.

Strict replace_block()

Requires unique targets, performs line matching, fails safely without mutating code.

Citations: Sarah Sachs · E4 | Notion Harness · B7 | AutoBE · E6 · 2026

Speaker notes

Sachs and the AutoBE team showed that tightening tool schemas dramatically cuts model errors. The model shouldn't be asked to edit files with regex strings; the harness should force strict, structural edits that fail early if the code has drifted. Keep it brief.

Act III · Engineering the Harness

Task isolation: One sandbox per run

Never run an agent directly in your workspace. Build a boundary: one task, one agent, one isolated git worktree.

  • Prevent overlapping branch mutations
  • Isolate processes from the host OS
  • Enforce strict capability-based network access
Citations: Geoffrey Huntley · F8 | Kenton Varda · F10 · 2026

Speaker notes

Modularity protects the codebase. Huntley observed that letting agents loose in a dirty workspace leads to overlapping bugs. By spinning up clean, isolated sandboxes with strict capability-based permissions, you prevent agents from accidentally modifying the wrong files.

Act III · Engineering the Harness

Executable feedback

Provide the agent with a failing test or a deterministic rubric, never a vague natural-language critique.

  • Write exact spec expectations in test templates
  • Execute linters and compiler judges on each save
  • Format raw compile errors into trace steps
Citations: Matt Pocock · F3 · 2025 | Viv Trivedy · D8 · 2026

Speaker notes

Matt Pocock famously tweeted that writing a failing test first is the best way to steer an agent. Instead of saying "fix the layout," write an assertions test. The harness runs it and provides structured errors. Evals become training data for the loop.

Act III · Engineering the Harness

Architectural guardrails

Mechanical code constraints are infinitely more effective than nagging prompts telling the model what to avoid.

Prompt Instructions (Vibe)

"Do not import legacy utility packages."

AST Policy Engine (Mechanical)

Harness linter pre-hooks reject AST violations.

Citations: steipete · F5 · 2025

Speaker notes

Steipete proved that parsing the AST in the harness caught code violations that prompt rules missed entirely. If you want an agent to follow clean architecture, don't write it in the prompt; write a linter rule in the harness. Let the machine enforce structure.

Act III · Engineering the Harness

Review as a harness stage

Tension: Should reviews be cooperative (supporting the builder) or adversarial (actively trying to break the changes)?

Cooperative Check

Simple lints, fast merges, high velocity. Risks leaking bugs.

Adversarial Check

Mock inputs, boundary tests, dual implementer validations.

Citations: shafty023 · F6 · 2026 | Matt Pocock · F4 · 2026

Speaker notes

This is tension slide 2 (debate slide). A good harness treats code review as a first-class engineering component, not an afterthought. Adversarial second agents or human gates prevent the build agent from validating its own mistakes. Settle on a hybrid model to balance speed.

Act III · Engineering the Harness

Durability & recovery

Long-running agent executions will fail. The harness must support checkpointing and resumption.

  • SQLite logs save execution nodes and context
  • Recovery hooks resume from the last valid step
  • Prevents expensive token waste from network drops
Citations: sydneyrunkle · F7 · 2026

Speaker notes

Runkle highlights that long-running agents crash due to infrastructure errors, not model errors. A production-grade harness must use durable execution libraries. Checkpoint the task list, commit files iteratively, and support dry-run recovery. Skip recovery details if brief.

Act IV · Improvement Loops & Self-Harness

Trace → eval → improve

Traces are the lifeblood of agentic engineering. Every pipeline failure must be mined to create a new evaluation case.

  • Mine raw logs for exact loop thrashing points
  • Convert failing steps into regression tests
  • Verify prompts and tools against tests
Citations: Viv Trivedy · D8 | LangChain Better Harness · C3

Speaker notes

Trivedy calls this the hill-climbing machine. Instead of guessing how prompts work, look at actual traces. If the model fails, write a regression test. That way, when you update tools or switch models, you know immediately if performance improved.

Act V · Future: Don't Impede the Model Path

Don't impede the model path

Build thin, measurable, swappable harnesses. Determinism where you can; probability where you must.

  • Avoid locked model-specific prompt cages
  • Build clean, swappable JSON API interfaces
  • Leave optimization space for smarter models
